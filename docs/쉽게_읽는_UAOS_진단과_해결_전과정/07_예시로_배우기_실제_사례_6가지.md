# 07. 예시로 배우기 — 이번 작업에서 실제로 있었던 사례 6가지

설명만 읽어서는 감이 잘 오지 않는다. 그래서 이번 작업에서 **실제로 일어난 일** 여섯 가지를 같은 틀로 정리했다. 모두 같은 다섯 칸으로 되어 있다.

| 칸 | 묻는 것 |
|---|---|
| ① 한 줄 비유(ELI10) | 열 살에게 설명하면 |
| ② 상황(입력) | 무엇이 주어졌나 |
| ③ 한 일(과정) | 어떤 순서로 했나 |
| ④ 결과(출력·증거) | 무엇이 나왔고 어떻게 확인하나 |
| ⑤ 배울 점(규칙) | 다음에도 쓰는 원칙 |

여섯 사례를 나란히 보면 다음 두 가지가 반복된다는 것이 보인다.

- "먼저 재현하고, 고치고, 같은 검사로 확인한다."
- "만든 사람이 아닌 다른 사람이 확인한다."

---

## 사례 1. 진단 — 음성사서함이 "받았다"고 거짓말을 했다

1. **ELI10**: 택배 기사가 "문 앞에 뒀어요"라고 문자를 보냈는데, 실제로는 택배가 없었다.
2. **상황**: 문서는 우편함이 "100% 무손실"이라고 했다. 코드를 읽어 보니 확인(ack) 함수가 파일이 없어도 성공을 돌려줄 것 같았다.
3. **한 일**:
   - 의심만으로 결함이라 부르지 않고, 재현 스크립트(`.coord/runs/U31/metaphor_probe.py`)의 P2 항목으로 실제로 일으켰다.
   - 메시지를 꺼내고, 시간이 흐른 척하고, 교환원 복구가 돌게 한 뒤 확인(ack)을 불렀다.
4. **결과**:
   - 수정 전 출력은 `P2 fresh claim treated as stale; ack reports a file it never wrote: CONFIRMED`였다. 방금 꺼낸 메시지를 "방치됨"으로 오판하고, 확인은 쓰지 않은 파일을 썼다고 보고했다.
   - 같은 스크립트를 수정 후에 다시 돌리면 `NOT_REPRODUCED`가 나온다.
5. **배울 점**: 코드를 읽어서 생긴 의심은 **가설**이다. 재현돼야 결함이다. 그리고 그 재현 스크립트가 나중에 "고쳐졌다"는 증거가 된다.

## 사례 2. 해결 — 빨간 테스트 먼저(red-first)

1. **ELI10**: 체온계로 열을 먼저 재 두면, 약을 먹은 뒤 같은 체온계로 "나았다"를 보여 줄 수 있다.
2. **상황**: 사례 1의 결함을 고쳐야 한다.
3. **한 일**:
   1. 결함을 그대로 재현하는 테스트 14개를 먼저 썼다(`tests/test_u32_mailbox_lossless.py`).
   2. 수정 전 코드에서 돌려 **12개가 실패**하는 것을 확인했다.
   3. 최소한으로 고쳤다. 꺼낼 때 시각을 새로 찍고(임대, lease), 옮기기가 성공한 뒤에만 원본을 지우고, 없는 파일이면 확인을 오류로 알린다.
   4. 14개가 모두 통과했다. 이어서 전체 회귀로 다른 곳이 깨지지 않았는지 봤다.
4. **결과**: 커밋 `353fa4c`. 테스트 14개(수정 전 12 실패 → 수정 후 0 실패).
5. **배울 점**: 고치기 전에 실패하는 테스트가 없으면, 테스트가 통과해도 그 결함을 고쳤다는 증거가 되지 않는다.

## 사례 3. 작업 지시 — 계약 매뉴얼로 README 세 줄 고치기(U35-P1)

1. **ELI10**: 심부름을 보낼 때 "적당히 사 와"가 아니라 "이 가게에서, 이 우유를, 이 돈으로, 영수증 받아 와"라고 쪽지에 쓴다.
2. **상황**: README의 낡은 숫자·링크 세 줄을 고쳐야 한다. 바꿀 문장은 지휘자가 이미 정했다.
3. **한 일**: 매뉴얼 첫머리에 기계가 검사하는 계약 칸을 썼다. 아래는 실제 파일(`.coord/tasks/U35-P1-readme-apply-manual.md`)을 줄인 것이다.

   ````text
   ```contract
   work_id: U35-P1
   worker: apply                  ← 정답을 이미 아니 모델 없이 적용(토큰 0)
   inputs:
   - README.md sha256=2147…b3c9   ← 작업 시작 때 파일 내용의 지문(바뀌었으면 거부)
   allow:
   - README.md                    ← 이 파일 밖은 못 고침
   acceptance: python -c "…assert 'n=1' in t and '660' in t and 'docs/37' in t"
   judge: claude                  ← 작업자(apply)와 다른 판정자
   ```
   ````

   그다음 `pilot manual lint`(검사) → `pilot run --manual`(격리 사본에서 실행) → diff 대조 → 번들 승인 순서로 진행했다.
4. **결과**:
   - `PASS`, 토큰 0, 번들 `e9fcb89b…4d05` 반영.
   - 장부에는 `worker: apply`로 기록됐다.
   - 실행하는 과정에서 숨은 결함(프로젝트 폴더에 남은 소켓 파일 19개)을 하나 더 찾았다(`8a0c11f`).
5. **배울 점**:
   - 정답을 이미 알면 AI에게 받아쓰기를 시키지 않는다.
   - **실제로 한 번 돌려 봐야** 읽기로는 안 보이는 결함이 드러난다.
   - 반대 사례도 있었다. 매뉴얼에 적은 숫자 "660"은 반영 시점에 이미 663이 되어 있었다(B79). 숫자는 인수 명령이 그 자리에서 세게 해야 한다.

## 사례 4. 자가개선 관문 — 통과시키면 안 되는 후보가 통과했다

1. **ELI10**: "시험을 세 번 봐야 인정"이라는 규칙이 있는데, 같은 시험지를 세 번 복사해 내도 인정됐다.
2. **상황**: 자가개선 관문은 "전후 표본이 각각 3개 이상"을 요구한다. 재검토 중에 "같은 작업을 재실행하면 장부에 행이 여러 개 생긴다"는 점이 걸렸다.
3. **한 일**:
   1. 재현했다. 전 작업 1개(B1)와 후 작업 1개(A1)를 각각 세 번 재실행한 장부를 만들고 관문에 넣었다. 결과는 `ADOPT_CANDIDATE 3 3 []`였다. **통과해 버렸다.**
   2. 이것을 그대로 실패하는 테스트로 만들었다(`test_a_retried_task_counts_once`). 수정 전에는 실패했다.
   3. 작업 ID당 마지막 실행 한 행만 세도록 고쳤다. 후보 목록에 같은 ID가 두 번 있으면 `DUPLICATE_WORK_IDS`로 거부한다.
4. **결과**:
   - 같은 입력이 이제 `n=1`, `INSUFFICIENT_SAMPLES`로 거부된다.
   - 같은 방식으로 재검토해서 비슷한 구멍을 하나 더 막았다. 채택한 변경의 재검증을 다른 작업자의 실행으로 채울 수 있던 문제다.
5. **배울 점**:
   - 자가개선에서 가장 위험한 것은 "점수를 올리는 쉬운 길"이다(목표 해킹, objective hacking).
   - 관문 자신도 반례로 공격해 봐야 한다. 이번 두 구멍은 **작성자인 내가 만든 관문**에 있었다. 그래서 독립 검토가 필요하다.

## 사례 5. 교차 검증 — Codex가 Windows에서 찾은 결함(U37-W1)

1. **ELI10**: 내 방에서만 연습한 춤은 다른 무대에서 틀릴 수 있다. 다른 사람이 다른 무대에서 봐 줘야 한다.
2. **상황**: 설치기(U37) 테스트는 Linux에서 모두 통과했다. 사용자 PC는 Windows다.
3. **한 일**:
   - Codex에게 **정해진 범위의 과제**를 줬다. 명령 4개, 통과 기준, 중지 조건("새 테스트가 실패하면 같은 패스에서 고치지 말고 멈춘다")을 적었다.
   - Codex는 명령 1에서 실패 2건을 보고 멈추고, PR에 보고했다.
4. **결과**:
   - 실패 ①은 **실제 결함**이었다. 설치되는 실행기 파일 설명문에 `C:\Users\…`가 들어가면, 파이썬이 `\U`를 특수 문자(유니코드 이스케이프)로 읽어 **실행기가 아예 돌지 않았다**. Linux 경로는 `/`만 쓰니 드러나지 않았다.
   - 실패 ②는 테스트 쪽 결함이었다(경로 표기 기대값).
   - Linux에서 Windows 경로를 흉내 내는 테스트로 ①을 재현하고(수정 전 실패) 고쳤다(`b10ead6`). 같은 부류의 `file:///C:/…` 문제도 미리 고쳤다.
5. **배울 점**:
   - "내 컴퓨터에서 된다"는 증거가 아니다.
   - 좁은 과제, 통과 기준, **중지 조건**을 적어 주면 검증자가 멋대로 고치다 문제를 키우지 않는다.

## 사례 6. 모든 프로젝트 설치 — 미리보기와 되돌리기

1. **ELI10**: 가구를 들이기 전에 줄자로 먼저 재 보고(미리보기), 영수증을 챙겨 두면(백업) 안 맞을 때 반품할 수 있다.
2. **상황**: 사용자 요청은 "UAOS를 전역 규칙에 심어 어느 프로젝트에서든 가동"이다. 이는 사용자 홈 폴더의 설정 파일을 바꾸는 일이다.
3. **한 일**:
   - 기본을 미리보기로 만들었다. `--apply` 때만 쓰고, 쓰기 전에 백업한다.
   - UAOS가 넣은 부분에만 표식(`<!-- UAOS:BEGIN -->`)을 달아 그 부분만 교체·제거한다.
   - 가짜 홈 폴더에서 "설치 → 점검 → 제거"를 돌려, 원래 파일과 같아지는지 테스트로 고정했다.
4. **결과**:
   - 미리보기 표에 `CREATE / UPDATE / UNCHANGED / SKIP`이 나온다.
   - 깨진 JSON이나 사용자가 일부러 꺼 둔 설정은 `SKIP`으로 건드리지 않는다.
   - 제거하면 사용자가 원래 막아 둔 도구는 그대로 막혀 있다.
5. **배울 점**:
   - 남의 설정을 바꾸는 도구는 "보여 주기 → 백업 → 내 표식만 → 되돌리기" 네 가지를 먼저 갖춘다.
   - 아직 실제 PC에는 설치하지 않았다. 첫 실제 설치 때도 미리보기부터 본다.

# 03. 해결 — 무엇을 어떻게 고쳤나

모든 수정은 같은 순서로 했다.

```mermaid
flowchart LR
    R[결함 재현<br/>실패하는 테스트 먼저] --> F[최소 수정]
    F --> T[그 테스트 통과]
    T --> G[전체 회귀<br/>다른 곳이 안 깨졌나]
    G --> D[기록<br/>docs·PLAN·커밋]
```

이 순서를 "빨간 테스트 먼저(red-first)"라고 부른다. 고치기 전에 실패하는 테스트를 만들어 둬야, 고친 뒤 통과했을 때 "정말 그 결함이 고쳐졌다"는 증거가 된다.

## 1. 음성사서함(mailbox) — "확인 전까지 절대 사라지지 않는다" [구현]

| 이전 | 이후 | 증거 |
|---|---|---|
| 꺼낸 직후 "방치됨"으로 오판 | 꺼낼 때 시각을 새로 찍음. 이를 임대(lease)라 한다 | `tests/test_u32_mailbox_lossless.py` 14개(수정 전 12개 실패) |
| 처리 확인(ack)이 거짓 성공을 보고 | 파일이 없으면 오류로 알림 | 같은 파일 |
| 되돌릴 때 원본을 먼저 지워 유실 | 옮기기 **성공을 확인한 뒤에만** 원본 삭제 | 같은 파일 |
| 같은 번호, 다른 내용 | 어디에 있든 "한 번호 = 한 내용" | 같은 파일 |
| 깨진 파일이 영원히 숨음 | `bad/` 폴더로 격리하고 브리핑에 표시 | 같은 파일 |

이 방식을 "최소 1회 배달(at-least-once delivery) + 같은 번호 중복 제거"라고 한다. 둘을 합치면 **유실도 중복 처리도 없다**.

## 2. 24/7 교환원(sentinel) — "지켜보다가 급할 때만 벨" [구현]

- 정리가 필요한 작업을 제대로 찾는다. 작업 결과와 같은 판정 기준을 쓴다.
- 모든 작업 폴더를 점검한다.
- 오래 방치된 메시지를 600초 뒤 회수한다.
- 점검할 때는 메시지를 꺼내지 않고 읽기만 한다(peek). 다른 도구를 방해하지 않기 위해서다.
- **벨**: 급한 알림(P1)이 있고 Codex 출석이 ACTIVE일 때만 `codex queue`로 한 번 알린다. Codex가 자리에 없으면 우편함에 보관했다가 돌아오면 울린다.
- 모델을 부르지 않는다. 정해진 규칙만 쓰므로 유료 토큰이 0이다.
- 증거: `tests/test_u32_sentinel_bell.py` 16개.

## 3. 비둘기 퇴출 — "사람이 말을 전하지 않아도 된다" [구현]

- **출석부(presence)**: 도구마다 `.coord/presence/<도구>.json`에 "지금 있음"과 만료 시각을 적는다. 만료가 지나면 스스로 UNKNOWN이 된다. 사람이 "Codex 부재"라고 적을 필요가 없다.
- **결과 자동 보고**: 작업(파일럿)이 끝나면 조율 기록(스트림)에 자동으로 남는다. 기본으로 켜져 있다. 테스트는 이 기능을 꺼서 실제 기록을 오염시키지 않는다.
- 증거: `tests/test_u33_pilot_autolog_default.py` 7개.

## 4. 계산기와 작업자 하네스 — "시킨 것만, 틀리면 기계가 막는다" [구현]

하네스(harness)는 말에게 씌우는 마구다. 작업자가 정해진 길로만 가게 하는 장치를 뜻한다.

| 장치 | 하는 일 |
|---|---|
| 계약 매뉴얼(contract manual) | 매뉴얼 첫머리의 ```contract 칸을 기계가 검사한다. 입력 파일 지문(SHA-256), 허용 범위, 인수 명령, 판정자 ≠ 작업자를 확인한다. 검사에 떨어지면 실행 자체를 거부한다 |
| 받아쓰기는 모델 없이(`worker: apply`) | 정답 코드가 매뉴얼에 이미 있으면 모델을 부르지 않고 그대로 적용한다. 토큰 0, 환각 0 |
| 출력 가드(output guard) | 문법 오류, **요청하지 않은 함수 삭제**, 허용 범위 밖 변경을 거부한다 |
| 구조화 출력·고정 seed | Ollama 출력 형식을 JSON 스키마로 강제하고, 같은 입력에 같은 출력이 나오게 해서 실패를 재현할 수 있게 한다 |

- 증거: `tests/test_u34_precision_harness.py` 30개(수정 전 25개 실패).
- 실제 실행 1건(U35-P1): 토큰 0으로 README를 고쳐 승인·반영까지 마쳤다.

## 5. 자가개선 관문(RSI evidence gate) — "제안은 기계가, 채택은 다른 사람이, 증거는 장부에서" [구현]

자세한 설명은 [04장](04_자가개선_RSI와_자가치유_쉽게.md)에 있다. 핵심만 적으면 다음과 같다.

- 명령: `rsi report`(현황), `rsi propose`(처방), `rsi gate`(관문), `rsi adopt`(채택), `rsi rollback`(되돌리기).
- 관문이 거부하는 것:
  - 평가기·장부를 건드린 변경.
  - 숫자를 직접 적어 넣은 후보.
  - 작성자가 스스로 검증한 후보.
  - 기준을 느슨하게 하는 변경.
  - 한 지표만 좋아지고 다른 지표는 나빠진 결과.
  - 이전 변경의 재검증이 끝나기 전의 두 번째 변경.
- 교환원은 한 작업자 유형의 실행이 10회 쌓일 때마다 검토 메시지를 **한 번** 보낸다.
- 증거: `tests/test_u36_evidence_gated_rsi.py` 27개.

| 항목 | 상태 |

- 증거: `tests/test_u37_install_everywhere.py` 20개. 설치하고 제거하면 원래 파일과 똑같이 돌아오는지까지 확인했다.

실패 1(B75)이 무엇인지는 다음과 같다.

- POSIX(Linux·macOS)에서 강제 종료된 통신 브로커를 같은 주소로 다시 켜면 "주소 사용 중"으로 실패한다.
- Windows의 이름 있는 파이프(Named Pipe)는 프로세스와 함께 사라지므로 이 결함과 관계없다.
- 고치려면 살아 있는 브로커를 가로채지 않도록 접속 시험 뒤에만 정리하는 설계 변경이 필요하다. 그래서 Antigravity용 작업 매뉴얼(U35-A1)로 넘겼다.

# 02. 진단 — 무엇이 문제였나

## 진단은 이렇게 했다: "읽기 → 재현 → 분류"

1. **읽기(read)**: 문서가 약속한 것과 코드가 실제로 하는 것을 나란히 놓는다.
2. **재현(reproduce)**: 의심 가는 곳을 짧은 프로그램으로 실제로 일으킨다. 재현이 안 되면 결함이라고 부르지 않는다.
3. **분류(classify)**: 결함의 뿌리를 가린다. 코드 결함인지, 연결 누락(wiring)인지, 환경 문제인지, 문서 과장인지 본다.

비유로 말하면 이렇다. 의사가 "아파 보인다"로 끝내지 않고 검사를 해서 수치로 확인하는 것과 같다. 수치가 나와야 치료 뒤에 "나았다"를 같은 검사로 증명할 수 있다.

### 판정 사다리 — "구현됐다"의 네 단계

| 단계 | 질문 | 예 |
|---|---|---|
| ① 설계됨(designed) | 문서에 규칙이 있나 | "유료 모델로 기다림 폴링 금지"라는 문장 |
| ② 구현됨(implemented) | 그 일을 하는 코드가 있나 | 고착 메시지 복구 함수 |
| ③ 연결됨(wired) | 실제 운영 경로에서 그 코드가 불리나 | 교환원이 매 주기 복구 함수를 부르는가 |
| ④ 운영 증거(operated) | 실제로 돌아간 기록이 있나 | 장부·스트림 기록 |

가장 흔한 결함은 **②는 있는데 ③이 없는 것**이었다. 부품은 있지만 서로 연결되지 않은 상태다.

## 진단 목록

### A. 기반 결함 — 전수 분석과 비판적 재검토에서 발견

| # | 쉬운 말 증상 | 왜 문제인가 | 어떻게 찾았나 | 수정 |
|---|---|---|---|---|
| A1 | 검사(테스트)를 돌리면 실제 사용량 장부에 **가짜 기록**이 생겼다 | 절약 효과를 재는 장부가 오염되면 모든 측정이 틀어진다 | 검사 전후 `.coord/usage/runs.jsonl` 생성 여부 비교 | `c0cdd46` |
| A2 | 상황판 명령(`coord status`)의 보고 수가 **항상 0** | 상황판이 거짓이면 사람도 도구도 오판한다 | 기록을 넣고 명령을 실행해 비교 | `b90f6bc` |
| A3 | 대소문자를 구분하는 컴퓨터(Linux)에서 규칙 파일 `CLAUDE.md`·`AGENTS.md` 변경을 **감시하지 못했다** | 작업자가 규칙 파일을 바꿔도 격리 검사가 놓친다 | Linux에서 감시 목록 출력 | `8ace86f` |

재검토에서는 앞선 분석의 오류 2건도 바로잡았다.

- "P09가 근거 없이 코드를 추가했다"는 틀렸다. 실제로는 P08이 지운 것을 복구한 것이었다.
- "공식 회귀가 장부를 격리한다"도 틀렸다. 실제로는 격리하지 않았고, 이것이 A1의 원인이었다.

### B. 5대 비유 감사 — 재현 스크립트 `metaphor_probe.py`

| # | 비유 | 재현된 증상(쉬운 말) | 뿌리 |
|---|---|---|---|
| P1 | 음성사서함·교환원 | 이미 처리한 보고가 다음 점검 때 **다시 도착** | 동기화 위치 기억(커서) 없음 |
| P2 | 음성사서함 | 방금 꺼낸 메시지를 "오래 방치됨"으로 오판해 되돌리고, 처리 확인(ack)은 **쓰지 않은 파일을 썼다고 보고** | 꺼낼 때 시각을 갱신하지 않음, 거짓 성공 반환 |
| P3 | 음성사서함 | 같은 번호로 다른 내용이 오면 되돌려 놓을 때(nack) **둘 중 하나가 사라짐** | 옮기기 성공 확인 전에 원본 삭제 |
| P4 | 24/7 교환원 | 정리가 필요한 작업을 점검이 **항상 못 찾음** | 점검이 엉뚱한 칸(verdict_hint)을 봄 |
| P5 | 24/7 교환원 | 급한 알림이 **우편함 파일로만** 남고 아무도 깨우지 않음 | 벨(알림 전송)이 연결되지 않음 |

그 밖의 감사 결과는 다음과 같다.

- **계산기(Ollama)**: 요약·위치 찾기 같은 "읽기 계산"은 실측으로 유료 토큰을 85.9~91.8% 줄였다. 하지만 "쓰기 계산"은 지휘자가 코드를 다 적어 주고 받아 적는 받아쓰기였다. 한 번은 요청하지 않은 41줄을 지웠다(P08).
- **전화기**: 유료 예약 호출 금지가 **문서 규칙뿐**이었다. 9/23에 실제로 15분 주기 예약 위반이 한 번 있었다.
- **비둘기**: 도구가 자리에 있는지(출석)를 여전히 **사람이 PLAN에 적어서** 선언했다.

### D. 자가개선(RSI)의 맹점 — 웹 조사와 코드 검토

- 공개 연구가 보여 준 공통 실패는 "문제를 푸는 대신 채점기를 속이는 것"이다. 목표 해킹(objective hacking)이라고도 한다.
- 이번 작업 전 UAOS의 자가개선은 **문서 규칙만** 있었고 코드는 없었다. 그래서 16개 맹점을 표로 만들고 모두 코드로 막았다.
- 자세한 내용은 [04장](04_자가개선_RSI와_자가치유_쉽게.md)과 [docs/38](../38_rsi-self-improvement-blind-spots-and-evidence-gate.md)에 있다.

### E. "모든 프로젝트에서 가동"의 맹점 — 설계 단계에서 발견

| # | 맹점 | 왜 위험한가 | 대응 |
|---|---|---|---|
| E1 | 전역 규칙 파일 3개는 다른 저장소의 **생성기가 덮어쓴다** | 규칙을 넣어도 다음 동기화 때 조용히 사라진다 | 설치기의 `--check`가 사라짐(drift)을 보고. 정본에도 넣어야 함 |
| E2 | Antigravity는 훅을 **자기 설정 폴더에서** 실행한다 | 현재 폴더로 프로젝트를 찾으면 늘 "프로젝트 아님"이 된다 | 훅 입력의 `workspacePaths`로 찾음 |
| E3 | Codex는 설정에서 기능을 켜야(`codex_hooks = true`) 훅을 실행한다 | 훅 파일만 두면 아무 일도 일어나지 않는다 | 설치기가 켬. 사용자가 끈 경우는 존중 |
| E4 | 훅이 **조용히 안 도는** 현장 보고가 있다(업데이트 뒤, 인증 방식) | "출석"이 거짓일 수 있다 | 출석에 만료 시각이 있어 1시간 뒤 UNKNOWN. 벨은 ACTIVE일 때만 울린다 |
| E5 | 질문마다 실행되는 훅의 출력은 **매 질문에 붙는다** | 토큰 낭비 | 세션 시작 때만 한 줄, 나머지는 출력 없음 |
| E6 | Claude의 질문 제출 훅이 종료 코드 2를 내면 **질문이 막힌다** | 훅 오류가 작업을 멈춤 | 어떤 오류든 종료 코드 0 |
| E7 | 교환원이 두 번 뜨면 같은 일을 두 번 한다 | 중복 알림·경합 | 프로젝트당 하나만 실행(pid 파일) |

### F. 작성자 자신의 오류 (지우지 않고 남김)

오류를 남겨야 다음 판정자가 같은 함정에 빠지지 않는다.

| 오류 | 어떻게 드러났나 | 분류 |
|---|---|---|
| "100% 무손실" 문구를 낮추자고 권고했다 | 사용자 의도는 유실 0이었다. 목표를 유지하고 구현을 올렸다 | 의도 오독 |
| 결과 자동 보고가 "없다"고 했다 | U15부터 있었지만 기본이 꺼져 있었다 | 코드 탐색 누락 |
| RSI 경로 판별에서 `lstrip("./")`로 `.coord`의 점까지 지웠다 | 테스트를 쓰기 전 비판적 재검토에서 발견 | 구현 실수 |
| 교환원 검토 메시지를 첫 작업자에게만 보내는 초안 | 두 작업자가 동시에 창을 채우는 경우를 따져 보다 발견 | 경계 조건 누락 |
| Antigravity도 최종 판정자로 허용한 초안 | 정본 docs/31 §3과 대조해 발견(판정은 Codex, 부재 시 Claude) | 정본 미대조 |
